# Zeist Chess on the web

The browser sibling of the iPhone app: the same product, from phone to desktop. Home is a board, set up and
waiting, with a picker and one Play button. Settings holds the engines, the board, the pieces and the credits.
Engines are downloaded to the browser and play offline. Games are kept in the browser. Everything runs on your
device; the server only hands out files.

## What is here

| Path | What |
|---|---|
| `public/` | The app, served as it is: plain ES modules and plain CSS, no bundler. |
| `public/js/app.js` | Screens: Home, the game, Recent and one game move by move, Settings. |
| `public/js/board.js` | The board: theme, grain, coordinates, pieces that glide, tap or drag, promotion. |
| `public/js/play.js` | A game against an engine: turns, clocks, undo, resign, the end, adaptive levels. |
| `public/js/engine.js` | One engine at a time through `core/host.js`, at the level `core/levels.js` sets. |
| `public/js/shelf.js` | The catalog, downloads checked by sha256, packs kept in Cache Storage, delete, storage used. |
| `public/js/log.js` | Every game in IndexedDB, with the iPhone app's field names; PGN and JSON export. |
| `public/js/account.js` | Signed in with Zeist through `GET /api/me` on the same origin, else signed out. |
| `public/sw.js` | Offline: the app shell, the catalog and downloaded packs. |
| `public/fonts/` | Prata and Jost (SIL Open Font License 1.1, texts beside them). |
| `src/worker.js` | The Cloudflare Worker: serves `public/` under a base path and engine packs under `<base>engines/`. |
| `cloudflare.config.ts`, `vite.config.ts` | The Worker's configuration for `cf dev` and `cf deploy`. |
| `scripts/assets.mjs` | Prepares `public/`: copies `core/`, lights the pieces, lists the app shell. |
| `scripts/pieces.py` | The piece sets as lit SVGs, with the iPhone app's own lighting (`ios/scripts/pieces.py`). |
| `scripts/serve.mjs` | A plain Node server running the Worker's handler, for tests and quick play. |
| `test/run.mjs` | The headless test suite (Playwright, Chromium and WebKit). |
| `screenshots/` | Every screen, phone and desktop, from the last test run. |

`public/core/`, `public/pieces/` and `public/shell.js` are generated by `scripts/assets.mjs` and not committed.

## Run it

From `web/`, with Node 24 and Python 3:

```sh
npm install                      # cf, the Vite plugin and Vite, for cf dev and cf deploy
node scripts/assets.mjs          # copies core/, lights the pieces, lists the shell
node scripts/serve.mjs           # http://localhost:8790/ , engines from engines.zei.st
```

Options for `serve.mjs`: `--port 8790`, `--base /chess/engines/` to try a base path, and
`--engines ../engines/dist` to serve packs from disk when engines.zei.st can't be reached (after
`engines/build-all.sh`).

With Cloudflare's own dev server, running the real Worker in workerd:

```sh
npm run dev                      # cf dev: http://localhost:5173/ ; packs come from engines.zei.st
ZC_BASE=/chess/engines/ npm run dev # the same under a base path: http://localhost:5173/chess/engines/
```

`cf dev` runs Vite with the Cloudflare plugin and forwards no arguments; for another port run
`npx vite --port 5199` directly.

In development the R2 bucket is empty, so the Worker fetches packs from `https://engines.zei.st/`
(`ENGINES_ORIGIN`, set only outside production mode).

## Test it

```sh
PLAYWRIGHT_DIR=<playwright folder> node test/run.mjs            # Chromium and WebKit
PLAYWRIGHT_DIR=<playwright folder> node test/run.mjs chromium   # one browser
node test/units.mjs                                             # the clock and flag rules, no browser
```

`PLAYWRIGHT_DIR` is a folder where `npm i playwright && npx playwright install chromium webkit` was run
(Playwright is not a dependency of this repo). Add `--engines ../engines/dist` to use local packs.

It starts its own server under `/chess/engines/` and, in each browser: loads the app; checks "Zeist" at the top
left of Home (and its absence under a base outside `/chess/`); opens `/chess/engines/zeist` and plays the Zeist engine
from it; downloads Ethereal in Settings
(each file checked against its sha256); plays Stockfish Lite (fetched on first play) by tap and by drag; steps back
with the arrow keys; plays Ethereal; reloads with no network and continues the game with the engine still
answering; resigns, finds the game in Recent and steps through it; plays a timed game and checks its clocks;
changes theme and pieces; breaks the downloaded engine and checks for the calm message and a usable board; exports
PGN. In Chromium it also takes the desktop screenshots and checks the signed-in username with a stand-in
`/api/me`. Screenshots go to `screenshots/`.

## Deploying

The app's address is `/chess/engines/`. From `web/`:

```sh
npm install && node scripts/assets.mjs
CLOUDFLARE_ACCOUNT_ID=<your account> ZC_BASE=/chess/engines/ ZC_ROUTE='<your domain>/chess/engines*' ZC_ZONE=<your domain> npx cf deploy --mode production
```

`cf deploy` runs the build (`vite build` through the Cloudflare plugin), which copies `public/` as it is; run
`node scripts/assets.mjs` first so `public/core/`, `public/pieces/` and `public/shell.js` exist.

What the deploy creates or needs:

- **Worker** `zeist-chess`, from `cloudflare.config.ts`. `workersDev` and preview URLs are off, so it is reachable
  only through a route or a service binding.
- **Bindings:** `ASSETS` (the app in `public/`); `ENGINES`, the existing R2 bucket `zeist-chess-engines`, read
  only; `BASE`, the base path as text. `ENGINES_ORIGIN` is left out in production mode.
- **Route:** `ZC_ROUTE` on the zone `ZC_ZONE`, such as `zeist.gg/chess/engines*`. The pattern must match the base path.
  Being a more specific route than the Zeist Worker's, it takes those requests and leaves every other path to Zeist.
  Without `ZC_ROUTE` no route is published.
- **Base path:** `ZC_BASE` (default `/`). Every address in the app is relative to the page, so the same build works
  at any base; the Worker answers 404 to anything outside it and redirects `<base>` without its slash to `<base>/`.
- **Engine addresses:** `<base><id>` (an id from `catalog.json`, such as `maia`) serves the app, which opens Home
  with that engine picked (downloaded on first play, as Stockfish Lite is) and shows the plain `<base>` address.
  `<base><id>/` redirects to `<base><id>`. An engine address is one segment without a dot; the app's folders and
  `engines` are reserved (`RESERVED` in `src/worker.js`), so an engine id can never name a file or a pack. Don't
  publish an engine with a reserved id.
- **Packs** stay on this origin under `<base>engines/`, read from R2: engine workers must be same-origin scripts,
  and engines.zei.st sends no CORS headers.
- **The way back:** served one folder under `/chess/` (as `/chess/engines/`), Home shows "‹ Zeist" at the top left,
  linking to `/chess`, and the name moves to its own line. Anywhere else Home is unchanged.
- **Sign-in:** under zeist.gg the app reads Zeist's session through `GET /api/me` on the same origin (Zeist's Worker
  answers it), and "Sign in" goes to `/welcome?return=<base>`. Where `/api/me` doesn't answer with JSON (staging,
  local), the app is signed out. Nothing else on Zeist's API is called.
- **Headers:** the page carries its own content security policy (`'self'` only, plus `wasm-unsafe-eval` for
  engines). Pack files are served with long cache lifetimes; their integrity is checked against the manifest's
  sha256 on download.

No secrets are needed.

## How things work

- **Base path.** The app lives in one folder and refers to everything relatively: `js/app.js`, `engines/...`,
  `sw.js`. Screens are addressed after `#`, so there is only ever one page to serve.
- **Engines.** The catalog is `<base>engines/catalog.json`; a pack's files are `<base>engines/<id>/<file>`. A
  Web Worker must be a same-origin script and packs load their files relative to their own address, which is why
  the Worker serves packs from this origin. Downloading reads the pack's manifest and checks it against the
  catalog's record of it (`manifest_sha256`), fetches every file into a staging cache, checks its size and sha256
  against that manifest, and only then swaps it into Cache Storage (`zc-packs`) under that same address, the manifest
  last, so a pack is never half there and a failed update leaves the installed version whole. The service worker
  answers pack requests only from there, and only for files the kept manifest lists, online or not: never from the
  network. The shelf's downloads go past it to the network only with a key the page gave the service worker, which an
  engine's worker can't read. An engine starts only once the service worker answers for the page; after a hard
  reload, which skips it, the game says at once to reload normally.
- **What an engine may run: the pins.** Cache Storage belongs to the whole site, so nothing kept there (packs or the
  catalog copy) is trusted on its own. The root is in the service worker's own script: `scripts/assets.mjs` writes
  into `public/shell.js` (`self.PINS`) the `manifest_sha256` of every pack version the catalog lists, kept in
  `engine-pins.json`, which only ever grows, so packs installed from an earlier catalog still run. Before a deploy, the pins must cover every version in the published catalog as well as the local one (the two can differ while a pack waits to be published): a version that is not pinned cannot be installed. `sw.js` loads
  `shell.js` with `importScripts`; the browser fetches both from the network on every update check
  (`updateViaCache: 'none'` at registration), compares them byte for byte, and keeps them in the service worker's
  own script storage, not in Cache Storage, so no page script can rewrite them. Every time a pack file is served, the
  kept manifest must hash to a pinned value and the file must match that manifest. A manifest that isn't pinned is
  not served (and not removed). A file that fails its pinned manifest is damage: the pack is removed and its row
  says its files were changed in this browser, with Download.
- **A catalog change needs a web redeploy.** The pins come from `engines/dist/catalog.json` when the web is built. A
  pack version published without a redeploy of the web is listed but can't be installed: its row says the app needs
  to be reloaded to get it, and a redeploy carries its pin. Publish the catalog, then build and deploy the web.
- **Installed packs stay.** An installed pack keeps the version it was installed from (its kept manifest, whose
  sha256 was the catalog's `manifest_sha256` then). A newer version in the catalog is offered in Settings as
  "Update to version X"; nothing is updated or removed on its own, and an engine the catalog no longer lists still
  plays. A pack updated on the server after it was chosen is not installed silently: its row shows the version there
  is now, to download again.
- **The cost to measure.** Every pack file is read and hashed each time a worker starts, since a verdict kept in
  memory wouldn't see bytes written since. The largest pack (Stockfish, about 99 MB) is read and hashed at every
  start. Measure that on a phone.
- **What this doesn't stop.** A script running inside the Chess app's own pages, or one able to script a window
  under its folder, can still defeat these checks: it can ask the service worker for a download key, or drive the
  page itself. Serving the app from its own origin would remove the shared-storage part of that (no other path could
  write its Cache Storage); that is not done.
  Stockfish Lite is listed in the picker before it is downloaded and comes down when you first play it. The first
  download asks the browser, quietly, to keep the storage.
- **Engines that fail.** A worker that errors or does not answer is retried once (untimed games); after that the
  game shows "<engine> stopped before it could move, perhaps for lack of memory. Try again, or play a smaller
  engine." with Try again and Resign. The board never freezes.
- **Games** are kept in IndexedDB with the fields of the iPhone app's `GameRecord` (`ios/ZeistChess/Log/GameLog.swift`):
  `id`, `startedAt`, `endedAt`, `startFEN`, `fen`, `moves`, `san`, `result`, `ending`, `player`, `engineID`,
  `engineName`, `engineVersion`, `packSHA`, `level`, `adaptive`, `rating`, `engineSettings`, `seed`, `undos`,
  `timeControl`, `timeClass`, `clocks`, `clockLeft`, `appVersion` (`Web 0.1`), `account`, `accountHandle`,
  `upload`, `sentAt`. Signed in, games carry the account's owner tag and finished games are marked `waiting`;
  nothing is uploaded.
- **Clocks.** `core/host.js` already plays on a clock, so the web has them: no clock by default, or the iPhone
  app's presets (1 min, 1+1, 2+1, 3 min, 3+2, 5 min, 5+3, 10 min, 15+10). The clocks start with White's first move,
  stop while the game is out of sight, and a fallen flag loses unless the other side cannot checkmate. Undo is only
  in games without a clock.
- **Keyboard.** In a game and in Recent: left and right arrows step through the moves, Home and End (or up and
  down) go to the start and the end, Escape lets go of a selected piece. During a game, stepping back shows the
  earlier position; the right arrow or the last move comes back.
